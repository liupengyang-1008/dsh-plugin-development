# 第 13 章 与 AI Agent 结对开发（本手册的用法）

> **这一章是本手册区别于普通文档的核心。** 你不需要成为程序员，但必须成为**好的验收者**。

## 13.1 一条铁律：**要求「出处」，否则不予采纳**

大模型会用**训练记忆**回答你的问题——而它的记忆里混杂着：
- Cordis **旧版本**的 API（比如 `onReady` / `onDispose` 这类钩子，**在本仓库里根本不存在**）
- 别的插件框架的写法（VS Code、Obsidian、Webpack 的插件 API 长得很像，但完全不同）
- 第三方生态项目的东西（比如 `dsh-market`，**官方仓库里没有这个**）

**所以，你的标准指令是**：

> 每一条 API、每一个字段名、每一条命令，都要给出它在本地仓库中的**文件路径 + 行号**。找不到出处的，直接说"未找到"，**不允许推测**。

**这条指令能过滤掉 90% 的幻觉。** 因为真正的幻觉是给不出出处的——你只要去核对一下就行（用编辑器的全局搜索，或者让另一个 Agent 去核对）。

## 13.2 五个提示词模板（直接复制改用）

### 模板 1：任务启动（每次都用）

> 我在 `<DSH 检出路径>`（DSH，版本 0.1.7-rc.1）里开发插件。
> **任务**：（一句话描述需求）
> **请你先做三件事，再动手写代码**：
> 1. 从 `docs/user/develop/basic/` 与 `docs/cordis-tutorial/` 里找出与这个任务相关的官方文档，列给我；
> 2. 判断我这个需求属于哪一类（工具 / 命令 / 事件拦截 / 终端能力 / UI 插件 / 设置卡片），说明依据；
> 3. 给出你打算创建/修改的**文件清单**，等我确认。
>
> **约束**：所有 API 必须标注仓库出处（文件路径 + 行号）；找不到就说"未找到"。**不要发明字段名。**

### 模板 2：代码审查（写完必做）

> 请审查你刚写的插件，逐条回答：
> 1. 导出形态是否正确？（函数插件必须是命名导出 `name`/`inject`/`Config`/`apply`，**不能有 `export default`**）
> 2. `inject` 数组里的每个服务名，是否在仓库里真实存在？给出出处。
> 3. 有没有硬编码的可调参数？（官方硬规矩：不同部署可能不同值的参数必须是 Config 字段）
> 4. 有没有用了可选服务却写成 `ctx.<name>`？（**必须**用 `ctx.get(name)`）
> 5. 我对资源的管理是否都通过 `ctx.effect` / `ctx.on` / `ctx.tools.register` 的返回值完成？有没有漏掉的裸资源？
> 6. 有没有任何地方是我"推测"的？请单独列出来。

### 模板 3：排错（插件没反应）

> 我的插件没有任何反应。请按顺序排查并报告：
> 1. 读启动日志，找 `pending (waiting for service:` 这一行，告诉我缺哪个服务；
> 2. 用 `dsh --profile <name> --dump-config` 的输出，确认我的插件行在不在、在哪个层；
> 3. 检查我的 `inject` 拼写与服务的提供方；
> 4. 检查导出形态（有没有混入 `export default`）；
> 5. 如果以上都没问题，给我一个最小复现步骤。
> **禁止**在没有证据的情况下让我"改一行试试"。

### 模板 4：版本升级前评估

> 我准备把 DSH 从 commit `（旧）` 升到 `（新）`，我的插件可能受影响。
> 请：
> 1. 用 `git log --oneline <旧>..<新> -- docs/user/develop docs/cordis-tutorial packages/core/tools packages/client` 找出可能影响插件 API 的提交；
> 2. 用 `git log --oneline <旧>..<新> --grep='!'` 找出**破坏性变更**（本仓库用提交标题里的 `!` 标记 breaking change，**没有 CHANGELOG**）；
> 3. 逐条说明对我的插件有没有影响，需要改哪里。

### 模板 5：抄范本（最快的学习方式）

> 我要写「（需求）」。请先在仓库里找出**最接近的现成实现**（给出包路径、主文件行数），
> 然后**逐行给我讲解它**，最后再基于它改造出我的版本。
> 官方推荐的范本清单见本手册附录 B。

## 13.3 十条红线（Agent 违反任何一条，都要打回）

| # | 红线 | 为什么 |
|---|---|---|
| 1 | 发明仓库里不存在的 API | 幻觉是最大的时间黑洞 |
| 2 | 在命名导出插件里加 `export default` | 官方事故：`inject` 会被丢弃（postmortem 0001） |
| 3 | 用 `ctx.<name>` 读**未在 `inject` 中声明**的服务 | 属性代理对拓扑敏感，会莫名失败 |
| 4 | 把权限/审批写成 `defineTool` 的字段 | 没这个字段。权限走 `tools/pre-execute` |
| 5 | 观察型 waterfall 监听器忘记 `next()` | 会静默吞掉下游所有默认行为 |
| 6 | 客户端插件跨插件导入**运行时值** | 被 bundle 纯净度门禁拒绝，只能 `import type` |
| 7 | 在 UI 里引入组件库 / Tailwind | 官方明确禁止，用 CSS Modules + `--dsw-*` |
| 8 | 硬编码可调参数 | 官方硬规矩 |
| 9 | 把 `presentCall` / `presentResult` 写成有副作用的函数 | 必须是纯函数（实时流 + 回放都跑） |
| 10 | 只写浏览器半侧、不写 Host 半侧 | Loader 无法 import，会失败 |

## 13.4 每课的标准交付物（拿去当验收模板）

完成任何一级后，你应该能拿出这五样：

1. **文件清单**：改了哪些文件、各自作用
2. **出处表**：每个 API 对应的仓库文件路径 + 行号
3. **验证记录**：跑起来的截图 / 终端输出
4. **验收清单**：本手册对应章节末尾的 ✅ 清单，逐项打勾
5. **已知限制**：哪些没做到、哪些是推测

## 13.5 关于「信任但验证」

本手册的所有事实，都来自仓库里的文档与源码。但**即使是本手册，也可能有笔误**。养成习惯：

> 当 Agent 或本手册告诉你某个 API 时，让 Agent 再执行一次核对：
> 「请用 grep 在 `deepseek-harness` 仓库里搜出这个 API 的定义位置，并把定义原文贴给我。」

**能贴出定义原文的，才是真的。**

# 第五篇 · 与 AI Agent 结对开发

> 这一篇是给"**零经验 + 让 AI 帮我写**"这个组合专门设计的。
> 主手册第 13 章讲了方法论，这里给**可直接复制的提示词**。

## 5.1 一条铁律

> **要求「出处」，否则不予采纳。**

DSH 处于 pre-stable 阶段、API 每周都在变。AI 模型对 DSH 的"记忆"极可能是**幻觉**（尤其是那些看起来很合理的 API 名）。
**每一个 API、字段名、配置项，都要让它说出处**：官方文档路径、源码文件+行号，或 commit 哈希。

**拒绝这三种回答**：
- "一般来说 / 通常 / 按照惯例……" → 要求给出 DSH 里的具体依据
- "这个 API 应该叫 xxx" → 要求给出所在文件路径
- "我查不到但大概是……" → 直接判定为幻觉，删掉

## 5.2 通用提示词模板

### 模板 A · 开工前先做调研

```
我要做一个 DSH 插件，需求是：<一句话需求>

在写任何代码之前，请先做调研并回答：

1. 这个需求应该做成哪种形态？（零代码组合包 / 工具插件 / 命令插件 /
   UI 插件 / 服务插件 / 组合包覆盖层）依据是什么？
2. 需要哪些服务？（去查官方包目录 packages/*/*/src 里的真实 inject 数组）
3. 需要监听哪些事件？是 waterfall 还是普通事件？
4. 有没有类似的官方插件可以当范本？给出包路径。
5. 有没有官方文档覆盖这个场景？给出文档路径。

铁律：每个结论必须给出处（文件路径 / 文档路径 / commit 哈希）。
查不到就写"未找到"，不要猜、不要编 API 名。
```

### 模板 B · 写代码（带硬约束）

```
请按以下硬约束写这个 DSH 插件：

【形态】函数式插件（绝大多数情况）
- export const name = '...'
- export const inject = [...]
- export function apply(ctx, config) { ... }
- 🔴 绝对不要写 export default

【如果需要提供服务】
- export default class extends Service，constructor 里 super(ctx, '<服务名>')
- 和上面的函数式形态**二选一**

【生命周期】
- 所有注册（tools/commands/slots/settings/监听器）必须包进 ctx.effect 并返回 disposer
- ctx.effect 的第二个参数写人类可读标签，格式 '包名: 说明'

【工具（如果用 defineTool）】
- parameters 用 DSH DSL：根是隐式对象，直接铺字段名，不写 type:'object'/properties 包装
- 必填用属性级 required: true
- output.schema 描述返回值结构；output.render 返回 [{type:'text', text}]
- execute 只返回纯数据，逐字段把 unknown 收窄

【UI（如果是 UI 插件）】
- package.json 必须有 exports["./client"] 和 dsh.client，files 必须含 lib/client.js
- 浏览器半侧里 @deepseek-ai/* 只能 import type
- 插槽用 ctx.slots.inject('<插槽名>', () => ctx.slots.register({name:'<插槽名>'}, 组件))

【代码注释】
- 每个非显然的决定，注释里写出你引用的 DSH 出处（文件路径或文档路径）
```

### 模板 C · 验收（防止"看起来能跑"）

```
请为这个插件列出验收清单。每条必须是**可执行的命令或可观察的现象**，
不要写"应该能正常工作"这种话。

必须包含：
1. 一条能证明「插件的真实加载路径」的命令
   （注意：手搓 ctx.plugin() 的测试不算 —— 它绕过了 Loader 的 export 解析）
2. 一条能证明「注册表贡献在 dispose 后被移除」的测试
3. 一条能证明「用户可见输出」的测试
4. `=--dump-config` 的预期输出（我该怎么确认我的行进了装配树）

每条都要写清：跑什么命令、看到什么算通过。
```

### 模板 D · 排错（把错误信息原样递过去）

```
我的 DSH 插件不工作了。以下是原始信息，请不要猜测：

【我做了什么】<步骤>
【我看到的完整错误信息】
<原样粘贴，不要概括>
【相关文件】
<package.json / cordis.patch.yml / src/index.ts 的内容>

请按这个顺序排查，每步给出你判断的依据：
1. 这个报错字符串在 DSH 源码/文档里的出处是什么？（先查清楚，再解释）
2. 可能的根因有哪些？按可能性排序，各自给依据。
3. 逐个验证：我该跑什么命令来确认/排除每一个？

不要给我"试试看"的建议。每条建议都要能说清"如果这个假设对，会看到什么"。
```

### 模板 E · 升级适配（API 变了）

```
DSH 从 <旧版本> 升级到 <新版本>，我的插件可能受影响。

请：
1. 先找出这个区间里的破坏性变更（查 CHANGELOG / git log --grep='!' /
   官方 postmortem / docs）。
2. 逐条对照我的代码，指出哪些地方会被破坏。
3. 给出修改前后的代码对比。

铁律：查不到破坏性变更记录就明确说"未找到"，不要凭印象说"应该没变"。
```

## 5.3 每个模板末尾都该问的三个问题

给 AI 的收尾三问，能挡掉绝大多数幻觉：

1. **"你刚才用到的每一个 API / 字段名，出处是什么？"**
2. **"这里面有没有你查不到、但根据经验推测的部分？如果有，明确标出来。"**
3. **"如果要推翻你的方案，最强的反方论据是什么？"**
