# 第 0 步（强制）· 版本闸门与防过时机制

> **这是本 skill 的第一道闸门，写在所有模板之前。**
> 本章回答一个问题：本 skill 的事实基线会腐化，怎么办。

---

## 1. 腐化是必然的，不是意外

| 事实 | 数据 |
|---|---|
| DSH 处于 pre-stable / rc 阶段 | 版本号 `0.1.5-rc.2` |
| 发布节奏 | tag 间隔中位数约 1.1 天 |
| 是否发生过破坏性变更 | 是（仓库用标题里的 `!` 标记破坏性提交） |
| 本 skill 的事实基线 | 官方 tag `dsh-v0.1.5-rc.2` / commit `c291e7961a` / 2026-09-10；对应**技能版本 `1.0.6`**（完整对照表：`13-version-history.md` §1.5） |
| 本 skill 的 references | **冻结在基线那一刻的快照**，随基线一起推进 |

**推导**：只要「把可变事实写进文档」这个动作存在，文档就会腐化。这是结构性的，不是谁疏忽。

**所以能承诺什么、不能承诺什么**：

- ❌ **不能承诺「不过时」。** 任何声称自己永不过时的 API 文档都在骗人。
- ✅ **可以承诺「过时会响」。** 把「静默产出错误代码」变成「响亮的失败」。

本 skill 的全部防过时设计，都服务于这一条：**不追求不过时，追求过时必被发现。**

---

## 2. 铁律 0：优先级反转

写 DSH 代码时，信息源的权威顺序（从高到低）：

```
1. 当前 DSH 源码                          ← 唯一权威
2. 探针脚本对当前源码的核验结果            ← 可执行的证据
3. 本 skill 的 references（快照）          ← 脚手架，不是权威
4. 模型记忆 / 常识                         ← 最低，禁止作为唯一依据
```

> **模板只是脚手架，不是权威。** 抄任何模板前，先确认它依赖的 API 还在。

这一条要在行为上体现：**如果源码和本 skill 冲突，永远以源码为准，并回来更新本 skill。**

## 3. 易变性三级：每条事实都归一级

| 级 | 含义 | 典型例子 | 使用规则 |
|---|---|---|---|
| **S**<br>结构性公理 | 架构约束，除非整体重构否则不变 | 函数式插件不得有 default export；`!!js` 只在 `config:`/`disabled:` 内求值；patch 逐行 last-write-wins；三种插件形态；`ctx.effect` 副作用回收 | **可直接用。** 开工时跑一次探针确认架构没被重构 |
| **M**<br>接口名 | 符号名 / API 名，会重命名、会迁移 | `defineTool`、`ParameterPropertySpec`、`ctx.tools.register`、`slots.inject`、事件名、插槽名、`dsh.bundle`、`--dump-config` | **每次使用前必须核验**（跑探针或 grep 源码） |
| **V**<br>实现细节 | 枚举、默认值、文案、数量、行号 | 斜杠命令清单、插槽总数、`$DSH_HOME` 默认值、报错文案细节、行号、字段默认值 | **不得作为代码假设。** 要写进代码就先从源码/运行时确认；否则显式声明「未核验」 |

**一句话判断法**：

> 这条事实如果明天变了，我的代码会崩吗？
> 会崩 → 它是 **M** 或 **V**，必须核验。
> 不会崩 → 它是 **S**，可以直接用。

**为什么要把「斜杠命令清单」划到 V 而不是 M**：它是**枚举**，新功能会往里加。把它当断言会让探针天天报假警，最后没人看探针。**探针只断言「一旦消失就会让指引失效」的事实** —— 这是探针可信度的前提。

**第四个维度：极性（N 级）。** 除易变性外，断言还有一个**正交**维度——极性。
否定性结论（「仓库没有 CHANGELOG」「不用 `BREAKING CHANGE:` 页脚」）的过时方向与正向**相反**：
不是东西消失了，而是东西**出现**了。正向断言机制在语义上抓不到它——搜不到反而被判定为成立。
因此探针为 N 级实现了**反向模式**（`nf:` 文件名 / `nd:` 目录 / `nt:` git tag / `nl:` 提交信息），
语义是**未命中 = HOLDS**（否定成立），命中 = STALE（否定已被推翻）。

完整的逐条登记见 `references/api-claims.md`。

## 4. 三问闸门（写任何 DSH 代码前，逐条回答）

### 第 1 问：我在对哪个版本写代码？

```bash
# 本地有仓库时
git -C <repo> rev-parse --short=10 HEAD
git -C <repo> log -1 --format=%cs
node -p "require('<repo>/package.json').version"

# 已安装 DSH 时
dsh --version
```

拿不到版本就**先要版本**。不知道版本而给出「API 一定如此」的结论，是耍流氓。

### 第 2 问：我要用的 API 属于 S / M / V 哪一级？

按第 3 节的判断法。**M 和 V 必须标记出来**，它们是你后面要核验的清单。

### 第 3 问：我能不能核验？

能 → 走第 5 节。不能 → 走第 6 节的降级规则。**没有第三条路**（禁止编造）。

## 5. 核验手段（成本从低到高）

```bash
# ① 探针脚本（首选，确定性、可批量、有退出码）
bash <skill>/scripts/dsh-api-probe.sh <DSH 仓库路径>
#    退出码 0 = 断言全部成立；1 = 有 STALE（相关模板可能已过时）；2 = 仓库路径不对

# ② 单点 grep（只想确认一个符号）
grep -rn "defineTool" <repo>/packages/core/tools/src/schema.ts

# ②-b 作者自报的破坏性变更（Conventional Commits 的 `type(scope)!:` 标题标记）
git -C <repo> log --oneline --grep='!:' <旧tag>..<新tag>
#    便宜，但**覆盖不全**：基线前的 tag 链上只有 7 条，且插件作者最痛的那几条
#    （模型 ID 改名、配置键 persona→personaPrefix、官方包移除）恰恰**没带 `!`**。
#    所以它是 ③ 的补充，不能替代 ③。索引见 13-version-history.md 第 2.5 节。
#    注意：`--grep` 默认基本正则 + 子串匹配，用 '!:' 最稳；
#    写 '^refactor!' 会漏掉 `refactor(cli)!:`（scope 夹在中间）。

# ③ 查「基线 → 最新」的真实差异（包增删 / 配置键 / 模型 ID / 会话格式版本）
bash <skill>/scripts/dsh-version-diff.sh <DSH 仓库路径>
#    需要本地是 git 仓库（含 tag 历史）；tarball/浅克隆不满足
#    脚本已内置 ②-b 的 `!:` 维度，正常情况下跑这一个就够

# ③-b 版本史速查（离线可用，无需源码）
#    见 references/13-version-history.md —— 16 个 tag 的逐版本破坏性变更表

# ④ 直接读源码（终极权威）
#    packages/*/*/src        —— 功能包
#    vendor/loader/src       —— 加载器 / 配置校验
#    packages/boot/app-boot  —— 启动、profile、补丁解析

# ⑤ 备选（需网络）：从 raw 源拉单个文件核验
#    仅在本地无仓库时使用，且必须在回复里注明「来源为远端快照、未与本地版本比对」
```

**探针的定位**：它只回答「我依赖的 API 名还在不在」。它**不**回答「你的插件能跑通」。两者不可互相替代。

## 6. 降级规则（拿不到源码时的强制行为）

**允许继续，但必须做到四条**：

1. **显式声明**：在回复里写明「以下 API 名未对当前版本核验；基于 `<版本>` 的文档，可能已变」。
2. **分层交付**：S 级的骨架可以照给；把 M / V 级的具体符号单独列成一张「**需你确认**」清单，而不是混在代码里蒙混过去。
3. **禁止既成事实**：不得把未经核验的 M / V 级事实写成肯定句。
4. **标注基线**：交付物里带一行出处注释：

   ```ts
   // DSH 插件 · 依 dsh-api-probe.sh 对 c291e7961a 核验通过
   // 升级 DSH 后请重跑: bash scripts/dsh-api-probe.sh <repo>
   ```

**绝不允许**：为了填补空白，编一个「看起来合理」的 API 名。
宁可写「这个名字我需要核验」——那句话是有价值的；编出来的名字是有害的。

## 7. 维护流程（探针报 STALE 之后）

```
1. 看 STALE 条目 → 定位失配的 M 级事实
2. 进 <repo> 读源码，找出当前正确写法
3. 更新 references/api-claims.md 该条：改写「基线写法」+「核验方式」
4. 更新 scripts/dsh-api-probe.sh 断言表里对应的模式
5. 若模板受影响 → 改 references/02-templates*.md / 03-api-cookbook.md 等
6. 重跑探针，确认 0 STALE
7. 把「什么 API 从什么改成了什么」写进 ~/.workbuddy/memory/
```

> ⚠️ 第 4 步有个已知陷阱：断言表的字段分隔符是**逗号**，所以**模式里不能出现字面逗号**（连 `[,]` 也不行）。写模式时用 `[^)]*` 之类的等价写法绕开。探针内置了字段数校验，会以 `PARSE` 报出这类错误。

### 维护时最容易犯的两个错（都真的犯过，写下来防重犯）

**① 用正则做「搜不到 → 所以不存在」的判断前，必须先用已知样本验证正则本身。**

本 skill 曾因此出过一次严重错误：统计「带 `!` 标记的破坏性提交」时用了
`git log --grep='^\(feat\|fix\|refactor\)\!'`，得到 **0 条**，于是写下「DSH 不用 `!` 标记」，
还把原本正确的 `git log --grep='!'` 当成错误从文档里删掉了。**实际有 21 条。** 正则有两个 bug：

- 它要求 `^refactor!`，而真实形式是 `refactor(cli)!:` —— **scope 夹在中间**；
- `git log --grep` 默认用**基本正则**，`\!` 是无效转义，`(feat\|fix)` 的写法也不可靠。

**规则**：任何否定性结论（「没有 X」「不存在 Y」）都必须先拿一个**已知存在的样本**喂给你的搜索式，
确认它能命中。命中不了 → 结论无效，不是事实为空。

**② 文档声称的能力，必须在脚本里真的实现。**

`dsh-version-diff.sh` 曾在头部注释里宣称覆盖「配置键改名」，但实现里只 diff 了包名与插件行，
`persona` → `personaPrefix` 这类改动**根本检不出来**——文档在说谎。
修复方式是补上 `configkeys()`：对 base 补丁的缩进键集合做 diff（排除 `name`/`config`/`id` 等通用键）。

**规则**：改脚本时逐个维度自问「我能为这一条给出一条**可复现的真实例子**吗」。给不出，就是没实现。

**③ 否定性结论现在有机器兜底了（N 级反向断言）。**

上面 ① 的教训已固化为机制：凡「没有 X / 不用 Y」类结论，都登记到 `api-claims.md` 第五节，
并把「若被推翻会看到什么证据」写成探针的 N 级断言（模式 `nf`/`nd`/`nt`/`nl`）。

> ⚠️ **N 级 STALE 的含义与正向不同。** 它不是「上游 API 过时」，而是**本 skill 的一条否定结论错了**。
> 处置方式也不同：不能只改一处——必须修正 `api-claims.md` 该条，再 **grep 全库**找出所有引用了
> 该结论的文档一并改正（正是上次漏做这一步，才让错误的「不用 `!` 标记」扩散进了多份文件）。

## 8. 版本落后于基线时：拉源码 → 出差异 → 刷新快照

**触发条件**：你要开发的 DSH 版本高于本 skill 基线（`v0.1.5-rc.2` / `c291e7961a`），或你不确定目标版本。

**不要做的事**：不要凭记忆推断「新版本大概改了什么」；也不要靠版本号推理——DSH 的版本号**不连续**（没有 `0.1.4`，`0.1.3-alpha.2` 之后直接是 `0.1.5-alpha.1`）。

### 三个命令

```bash
# 1) 拉取 / 增量更新源码到 <skill>/vendor/dsh-src/
#    首次约 200 MB，必须先经开发者确认（--yes 才跳过）
bash <skill>/scripts/dsh-sync.sh

# 2) 核验本 skill 的 48 条断言（43 正向 + 5 反向）是否仍成立
bash <skill>/scripts/dsh-api-probe.sh <skill>/vendor/dsh-src

# 3) 出「基线 → 最新」差异（输出可直接贴进 13-version-history.md 的表格片段）
bash <skill>/scripts/dsh-version-diff.sh
```

`dsh-sync.sh` 的开关：

| 开关 | 用途 |
|---|---|
| `--check-only` | 只探测远端最新 tag，不下载 |
| `--tarball` | 降级：只拉 master 源码快照（单次 HTTP，**无 git 历史**，`dsh-version-diff.sh` 不可用） |
| `--shallow` | 浅克隆：只要最新代码，不要 tag 历史 |
| `--mirror <前缀>` | 走镜像，如 `--mirror https://ghfast.top/` |
| `--repo <URL>` | 自定义仓库地址 |
| `--yes` | 跳过确认（**只在自动化里用**） |

### 三条纪律

1. **拉取前必须经开发者确认。** 首次克隆约 200 MB（`.git` 约 190 MB + 工作树）。脚本会打印目标路径、预计体积、来源 URL 后等待确认；后续更新是增量 `git fetch`，不会重下。
2. **拉下来的是「引用源」，不是「依赖」。** 只用于核验 API 与查变更历史。**绝不在 skill 目录执行 `pnpm install` / `npm install`**，也不要在插件工程里 `import` 它。
3. **拉不到源码时走第 6 节的降级规则**，不要凭印象补 API 名。

### 目录约定

```
<skill>/vendor/
├── dsh-src/         ← git 仓库，可增量 fetch（主路径）
├── dsh-snapshot/    ← tarball 模式的源码快照（无历史）
└── dsh-state.json   ← 同步状态：时间 / commit / tag 数 / 最新 tag / 基线
```

### 网络不可达时

`dsh-sync.sh` 会打印可操作路径，而不是抛一堆 git 报错：

1. 配代理后重试：`export https_proxy=http://127.0.0.1:7890`
2. 用镜像前缀重试：`bash dsh-sync.sh --mirror https://ghfast.top/ --check-only`
3. 改用轻量快照：`bash dsh-sync.sh --tarball`
4. **往往最省事的一条**：手上已有任意一份 DSH 仓库（如另一台机器克隆的），直接指给探针，完全不需要联网 ——
   `bash <skill>/scripts/dsh-api-probe.sh <你本地的 deepseek-harness 路径>`

### 拉下来之后

1. 把 `dsh-version-diff.sh` 输出的表格片段追加到 `references/13-version-history.md` 第 2 节。
2. 同步更新该文件第 1 节的 tag 总表。
3. `vendor/dsh-state.json` 由脚本自动写入；顺手更新你自己的基线声明。
4. 探针若报 STALE → 走第 7 节的维护流程。

## 9. 探针自身的可信度（改探针后必读）

**核心命题：一个不能失败的探针，比没有探针更危险。** 没有探针时你会保持警惕；探针报「全部成立」时你会放心照抄。所以**任何「没校验到东西却报通过」的路径都是必须修的缺陷**。

### 三个已实际发生的假通过（都来自本项目）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | bash 版打印「✅ 全部断言成立」并 `exit 0`，但 `total=0` | `CHECKS=$(cat <<'EOF' … )` 在缺 `cat` 的 shell 里**静默展开为空** | 断言表改内联字符串字面量；**新增空表哨兵**（空则 `exit 3`，不再报成功） |
| 2 | Python 版报出 2 条 STALE，但样本明明存在 | `scope` 既可指目录（`packages`）也可指**文件**（`packages/AGENTS.md`），代码只按目录处理 | 遍历函数同时支持「目录」与「单文件」两种入口 |
| 3 | 本机 bash 跑出 **37 条 STALE** | 该 bash 缺 `grep`/`head`/`find`，所有文本检索恒为失败 | 改用**纯 Python 探针**（零 coreutils 依赖），bash 版降级为备选 |

**共同教训**：失败模式**不是报错，而是静默地给出一个看起来正常的答案**。三次都发生在「环境能力缺失」或「输入形态超出假设」的时候。

### 强制自检流程（每次改完探针都要跑）

1. **正向**：对真实仓库跑，应 `stale=0` 且 `exit 0`。
2. **负向-路径**：传一个非 DSH 目录（如 `C:\Windows`）→ 必须 `exit 2`，且提示「看起来不是 DSH 仓库」。
3. **负向-断言**：造一个临时骨架目录，**塞进 N 级断言声称「不存在」的东西**（如 `CHANGELOG.md`、`packages/ui/`）→ 必须报出对应 N 级 STALE 并 `exit 1`。
4. **空表**：临时把断言表置空 → 必须 `exit 3`，**不得**报成功。

第 3 步是最容易被跳过、也最关键的一步 —— 它是唯一能验证「否定性结论的兜底机制真的接上了」的手段。

### 断言表的维护纪律

- **`.py` 与 `.sh` 两份断言表内容必须逐条一致**（等级、说明、模式、作用域全同）。改一份就要改另一份，否则两个探针会给出不同结论。
- **改断言前先用已知存在的样本验证正则**。`grep` 用的是 ERE，Python 用 `re`，两者转义规则不同（例：bash 风格的 `export \{\}` 在 Python 里仍能工作，但别指望所有写法都兼容）。
- **V 级事实一律不许进断言表**。枚举类事实（命令清单、插槽总数、默认值、报错文案细节）一断言就天天报假警，最终导致没人再信任探针。判断标准：**这条事实明天变了，会让本 skill 的指引失效吗？** 不会 → 不进表。

## 10. 诚实的边界（不要把这些当结论讲给用户）

- 探针只覆盖它断言过的 **48 条**事实（43 正向 + 5 反向），**不覆盖 V 级细节**。
- 探针通过 ≠ 插件能跑通，只说明「它依赖的 API 名还在」。
- 「装上了」永远不等于「生效了」——必须看到实际输出或界面变化。
- references 里带行号的引用，行号**一定会漂移**，行号只作为「基线时刻的位置记录」，核验时必须按符号名 grep，不能按行号找。
- 官方文档自身存在两处内部矛盾，本 skill 已选定立场并在 `11-glossary-and-provenance.md` 说明。
